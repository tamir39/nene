# Account transaction history

Implemented 3 November 2026 for PDF page 2, Account management, BR-08: customers can view their accounts' transaction history. Month selection also prepares the month-specific history destination required by BR-14; no chatbot is implemented by this change. The later [local transfer slice](LOCAL_TRANSFERS.md) adds TOTP-authorized synthetic transfer entries; [local cash operations](LOCAL_CASH.md) now post deposit/withdrawal entries; external payments remain unfinished. AWS stays undecided.

## Customer flow

Start the local demo with `run.bat`, sign in as a customer and choose **View history** under an account. The same screen supports checking, saving and mortgage accounts, including closed accounts still owned by that customer. Enter `YYYY-MM`, choose **Show month**, or return to **Current month**. **Load more** appends the next page. Back returns to the account workspace; sign-out removes protected screens and late responses cannot restore history.

Without a completed local demo transfer, deposit or withdrawal, the correct result is **No posted transactions in this month**. Successful local transfers and cash operations create actual debit/credit entries in this demo database. Opening a checking/saving account or preparing a sample mortgage schedule does not create a deposit, repayment or history entry. Automated tests use synthetic records only in disposable fixtures; none are inserted into the normal demo. A failed read shows an error instead of a fabricated empty result or zero transaction. Changing the month clears the previous results; a failed next-page request keeps the already loaded rows and permits retry.

Posted entries show kind, credit/debit in words and signs, exact amount/currency, posting time, posted status and operation reference. No pending authorization attempts or reference-photo activity appear as financial history. Officer history access is not added: the PDF calls for customers viewing their own history, and ordinary officer account assistance does not grant this new customer route.

## API and storage

`GET /api/v1/me/accounts/:accountId/history?month=2026-11&cursor=<optional-entry-UUID>` requires a verified active customer session. Account and cursor IDs must be UUIDs; month is required and limited to `2000-01` through `2100-12`. Unsupported/duplicate query fields are rejected. Responses are `Cache-Control: no-store`.

Response: `{ accountId, month, timeZone: "Asia/Bangkok", entries, nextCursor }`. Each entry has `id`, `reference` (operation UUID), `kind`, `direction` (`credit`/`debit`), `amountMinor` (positive integer string), `currency`, and `postedAt` (UTC timestamp). `nextCursor` is null at the end. There is no total-count claim, running balance, export or transaction mutation API.

The backend checks account ownership on every request, including every next page, and repeats the owner predicate in the entry query. Foreign and nonexistent accounts both return 404. Officers return 403, invalid authentication 401, malformed filters or a cursor outside the selected account/month 400, and dependency failure 503. The cursor identifies a persisted entry within that account/month, not client-supplied money or an offset. The query returns 25 entries ordered by posting timestamp descending and UUID descending, fetching one extra to detect a next page. Equal timestamps do not skip/duplicate rows; the database retains microsecond precision. This is keyset pagination, not a frozen snapshot: future newly posted entries are visible after refreshing. Completed local transfers introduce new entries.

Month boundaries and displayed times use **UTC+07 (Asia/Bangkok)** consistently, independent of the phone/browser timezone. This is an explicit project convention for the VND demo, not a PDF mandate. For example, November 2026 starts at 31 October 17:00 UTC and ends just before 30 November 17:00 UTC. Amounts remain integer strings/BigInt through display; no floating-point financial calculations are introduced.

`bank.account_history` is a read model with account FK, operation reference, kind, direction, positive integer amount, currency and posting timestamp. A unique `(operation_id, account_id)` pair prevents duplicate entries for the same account/operation; the paging index covers account, descending time and ID. RLS is enabled/forced, client-facing roles have no privileges, and `nene_api` has **SELECT only**. No insert/update/delete or balance-write privilege is added. Existing account data is untouched.

Other future financial posting must atomically change balances, consume the operation-bound authorization and insert the corresponding entries under narrow, reviewed permissions. It must establish the operation foreign key/record relationship, supported kinds/account rules, currency consistency, funding and identity policy before enabling writes. For local transfers, the operation UUID matches the immutable transfer receipt and consumed confirmation. Other operation kinds remain unimplemented. Do not manually seed normal-demo history and imply that a real transaction passed 2FA.
