## Scope and comparison

The [PDF](../FinalProject_2026_2027.pdf) requires integration with a payment service and names VNPay and Stripe as examples. One service is enough for that clause. Payment checkout does not also prove other-bank transfers, electricity/water fulfillment, phone top-up or booking coverage. Keep those requirements separate as recorded in the [scope audit](SCOPE_STATUS_AUDIT.md).

Compare hosted checkout options so Flutter only opens the provider page and reads Nene's result. Keep secrets, request creation and result verification in the existing NestJS API, with records in Supabase PostgreSQL. No second backend, custom card-entry form, wallet product, subscriptions or saved-card feature is needed. Relative effort below is an engineering assessment, not a completed integration benchmark.

## Setup effort and cost boundary

For VNPay, the remaining setup is obtaining `vnp_TmnCode`/`vnp_HashSecret`, choosing the test callback and return URLs, and confirming a test transaction reaches NestJS. Official docs link to [sandbox registration](https://sandbox.vnpayment.vn/devreg/), but the research tool timed out fetching that form. This is a limitation of this read, not proof the registration service is down or that issuance is immediate. No registration was submitted. VNPay's introduction explicitly requires internet access for server notifications. [VNPay setup guidance](https://sandbox.vnpayment.vn/apis/docs/gioi-thieu/).

The existing `run.bat` exposes a local/LAN preview, not a public callback. A later test needs a deliberately configured narrow HTTPS callback route, through a suitable hosted endpoint or controlled forwarding arrangement. Do not expose the entire preview/API/Auth proxy, database or Supabase services. No tunnel or hosting is created by this recommendation, and local ports/launcher files remain unchanged. Stripe's CLI forwarding is a genuine local-testing advantage, although it still needs account access and an active forwarding process. [Stripe webhook guidance](https://docs.stripe.com/webhooks).

Use provider test instruments and sandbox endpoints only. No live merchant contract, real charge, subscription or paid service is proposed. Live processing prices are not a useful tie-breaker for this bounded test; fees, approval, sandbox access conditions and any hosting/forwarding costs must be confirmed before choosing paid services. Do not claim an account or setup is guaranteed free based solely on the existence of test documentation. A provider sandbox remains distinct from our own simulated cash source; lecturer acceptance is still open.

## Proposed minimum flow

1. **One labelled sandbox payment request.** NestJS owns customer association, purpose, VND amount, expiry and stable operation reference. Use a small clearly labelled test order as integration evidence; do not add a shopping catalogue or claim that it fulfils a bill/booking. Pick the real assignment-facing payment purpose before final feature acceptance. The external test bank/card pays the sandbox merchant; it is not a Nene-account debit or automatic Nene deposit.
2. **Review and Nene authorization.** Reuse the existing confirmation patterns, with a distinct payment purpose bound to exact details and TOTP. Preserve applicable reference checks and block amounts at or above 5,000,000 VND while high-value identity remains unresolved. Provider test OTP is separate from Nene transaction-bound 2FA. Persistent pending intent/security metadata must not be presented as a completed transaction.
3. **Open hosted checkout.** Keep credentials in NestJS and payment-instrument entry on the provider page. In Edge, prefer an explicitly opened checkout tab while keeping Nene's memory-only session alive. Handle blocked tabs and re-login after refresh; do not put access tokens in return URLs or silently introduce persistent sessions. Native browser return/process-loss behavior needs later Android testing; it is not verified by Edge.
4. **Verify the server result.** Use the provider's documented signature and status contract; validate merchant, order, expected amount/currency and the authorization used to initiate the payment before committing a terminal outcome. A callback must not depend on a still-live browser session or a fresh TOTP; record an authenticated late settlement without creating a new payment. VNPay encodes its VND amount multiplied by 100: handle this at the adapter boundary without changing Nene's integer VND storage. Treat callback duplicates, retries and conflicting/late results safely and atomically. [VNPay PAY contract](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html).
5. **Display authoritative status.** A return-page query or client success message is not proof of payment. Nene reads its owned backend record and shows pending, paid, failed or cancelled only when established. Browser closure is not proof of cancellation. Retain the same operation for uncertain outcomes; do not automatically issue another charge. Record external payment evidence separately from bank-account entries unless an explicitly defined posting rule exists. This prevents displaying a false Nene debit or duplicate bank history.

This is proposed engineering support for BR-10/BR-04, not implemented behavior or a new user feature. Avoid a generic provider framework, multiple SDKs, recurring billing, refunds UI and marketplace infrastructure in the first slice. Use a minimal server-side status query only where needed to recover a missing notification under the selected provider's contract.
